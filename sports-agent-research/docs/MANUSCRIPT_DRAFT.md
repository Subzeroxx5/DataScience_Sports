Retrieval, Tools, or Both? A Controlled Comparison of Agent Architectures for Sportsbook Price Identification

Abstract

Large language model (LLM) agents increasingly rely on external information to answer questions that require current, verifiable data (Wang et al., 2023). That information reaches the model as retrieved documents, as the output of callable tools, or as some combination of the two. This study asks how agent architecture affects the accuracy, consistency, and freshness of an AI agent identifying positive expected value opportunities across multiple sportsbooks. We compare three architectures: retrieval-augmented generation, tool calling, and a hybrid of the two. We built a controlled research prototype with a synthetic sportsbook benchmark, deterministic ground truth, and a shared deterministic quantitative engine covering implied probability, no-vig normalization, leave-one-sportsbook-out market consensus, and expected value. The three architectures share every experimental control except architecture itself. All three use one locally hosted LLM, llama3.1:8b at temperature 0.0, applied identically. We ran 330 real observations, consisting of 11 scenarios crossed with 10 repetitions and 3 architectures, and analyzed them with paired nonparametric statistics (exact McNemar, Wilcoxon signed-rank, and Friedman) under a Holm-corrected alpha of 0.05. Tool-calling and hybrid architectures significantly outperformed the RAG-only architecture on best-line and best-odds accuracy (88.9% versus 100.0%, Holm-adjusted p=0.0059) and on completeness (median 0.75 versus 1.00, Holm-adjusted p=9.2e-11). The two were themselves statistically indistinguishable on every binary accuracy metric. Hybrid was significantly slower than tool-calling (median 22.7s versus 7.0s, Holm-adjusted p=5.3e-19) and showed no measured accuracy benefit over tool-calling alone. Consistency and freshness showed no distinguishable difference across architectures in this dataset. No architecture reached a full expected-value verdict in any observation, which we treat as a data characteristic rather than a result. We conclude that no single architecture dominates across all three primary outcomes. Architecture selection in this setting involves a tradeoff between accuracy and completeness on one side and latency on the other.

1. Introduction
   
Identifying the best available price for a sports betting market requires gathering current information from multiple sportsbooks and comparing it against a reference for value. This is a natural setting in which to study how AI agents obtain and use external information. The correct answer is determined by verifiable, structured facts, namely prices, rather than by subjective judgment. Value itself also has a defensible market-derived reference point in the form of a no-vig consensus across sportsbooks, even though that reference is not a claim about the true probability of the sporting outcome.
Modern LLM agents obtain external information in at least two structurally different ways. The first is retrieval-augmented generation (RAG), where the model reads snippets pulled from a document corpus (Lewis et al., 2020). The second is tool calling, also known as function calling, where the model invokes structured operations that return exact, typed data (Schick et al., 2023). Hybrid designs combine both. Each approach has its own failure modes. Retrieval can surface stale or incomplete evidence, and the model does not always recognize that evidence as stale. Tool calling depends on the model reliably orchestrating multiple calls in the right sequence. Freshness, meaning whether the information an agent ultimately relies on is current rather than outdated, is a particularly important and under-examined property in this domain, because sportsbook prices change continuously.
This motivates our research question. How does agent architecture, whether tool calling, retrieval-augmented generation, or a hybrid approach, affect the accuracy, consistency, and freshness of an AI agent identifying positive expected value opportunities across multiple sportsbooks?
Our contribution is a controlled, fully reproducible experimental framework that isolates architecture as the only meaningfully varying factor. The framework holds the LLM, its configuration, the scenario set, the query wording, the quantitative engine, and the evaluation methodology constant across all three architectures. We report the resulting statistical findings from a real, non-mock, 330-observation experiment using a single locally hosted model.

2. Background / Related Concepts
   
Large language model agents that answer questions using external, non-parametric knowledge sources have become a common design pattern (Wang et al., 2023). Retrieval-augmented generation supplies the model with passages retrieved from a corpus via semantic similarity search over embeddings (Lewis et al., 2020). Tool calling instead lets the model invoke predefined operations with structured arguments and receive structured results. This can make the model's final answer traceable to an exact data source rather than to free-form generated text (Schick et al., 2023). Hybrid agents that combine both channels, and that must reconcile disagreements between them, are a comparatively less studied design point (Singh et al., 2025).
Sportsbook betting markets quote prices as American odds, which imply a probability once converted. Sportsbooks build in a margin known as the vig or overround, so the raw implied probabilities across a market's outcomes sum to more than 1.0. These raw values must be normalized into no-vig or fair probabilities before they can be used as a probability reference (Shin, 1993; Štrumbelj, 2014). A market-consensus reference probability averages no-vig probabilities across sportsbooks, and it is often computed while leaving out the sportsbook under evaluation to avoid circularity. This is one common way to estimate a fair price against which a specific sportsbook's price can be compared for value (Wolfers & Zitzewitz, 2004). Expected value relative to such a reference is a standard framing for identifying favorably priced bets. A market-consensus probability is not a claim about the true probability of the underlying sporting outcome, because bookmakers set prices to manage their own risk rather than solely to forecast outcomes (Levitt, 2004).
LLM output reliability is a relevant concern whenever an agent's output feeds into a decision with real consequences (Huang et al., 2023). One aspect of this is the tendency of models to state claims not supported by their actual inputs, commonly called hallucination. Our architecture designs are built so that the final structured output can only contain data that was itself returned by a validated tool call or a provenance-checked retrieval. This structurally limits that failure mode, although it does not by itself prove the absence of it.

3. Methods

3.1 Research Design

The independent variable is agent architecture, at three levels: RAG-only, tool-calling-only, and hybrid. The primary dependent variables are accuracy, consistency, and freshness. Accuracy is measured through best-line accuracy, best-odds accuracy, and EV classification accuracy. The secondary dependent variables are completeness, unsupported-claim rate, latency, failure rate and category, and, for the hybrid architecture specifically, conflict-resolution behavior between its two information channels.

3.2 Controlled Benchmark
All experiments use a controlled, synthetic sportsbook benchmark. Games, markets, and per-sportsbook American-odds quotes are fixed, versioned data rather than live market feeds. Ground truth, meaning the correct best sportsbook and price for each scenario, is computed once, deterministically, and directly from this benchmark data. That computation is independent of any agent architecture, and the ground truth is never exposed to an agent as part of its input at any point in the pipeline. The final experiment used 11 scenarios, a representative subset of the full controlled benchmark. This subset spans positive-odds, negative-odds, and mixed-sign cases, a best-line tie case, a missing-sportsbook-data case, a current-versus-stale freshness case, and moneyline, spread, and total market types.

3.3 Architectures
RAG-only retrieves the top-k most similar documents from a vector index built over a controlled document corpus, using a sentence-transformer embedding model and an exact FAISS inner-product index. It extracts sportsbook price claims from that retrieved text and validates each claim's provenance against the retrieved documents before the claim can reach the final answer. It has no access to structured sportsbook tools.
Tool-calling-only runs a bounded multi-turn loop in which the model calls structured tools, backed by an OddsProvider abstraction, to fetch current game, market, and price data. The final answer is built exclusively from the actual structured values returned by tool calls and never from the model's own generated text, so a hallucinated claim cannot structurally reach the output. It has no access to the RAG corpus.
Hybrid has access to both channels. A deterministic, LLM-free reconciliation step decides, per sportsbook and outcome, which source is authoritative. Current structured tool data always takes precedence over a disagreeing RAG-derived price for the same sportsbook and outcome.

3.4 Shared Quantitative Engine
All betting-relevant arithmetic is implemented once and shared identically across all three architectures. This includes American-odds-to-implied-probability conversion, no-vig probability normalization, leave-one-sportsbook-out market consensus, probability edge, expected value, and market dispersion statistics. No architecture reimplements any of this math. The market-consensus reference probability this engine produces is not treated, in this study, as a claim about the true probability of the sporting outcome. It is treated only as a market-derived reference point.

3.5 Experimental Controls
The following were held identical across all three architectures for the final experiment: the LLM provider and exact model (llama3.1:8b, a locally hosted Ollama model, chosen so the experiment could run without per-call API cost), temperature (0.0), RAG retrieval depth (top_k=5), the tool-calling loop's iteration bound (6), the embedding model (sentence-transformers/all-MiniLM-L6-v2), the 11-scenario set, one canonical and architecture-neutral natural-language query per scenario with no per-architecture wording differences, the repetition count (10 per architecture and scenario), the shared quantitative engine, and the evaluation framework and metric definitions. The order in which the three architectures were executed was rotated deterministically across repetitions, for example RAG then TOOL then HYBRID, followed by TOOL then HYBRID then RAG, followed by HYBRID then RAG then TOOL. This rotation ensures that architecture identity is not confounded with execution order.

3.6 Experimental Procedure
The experimental configuration was frozen in a version-controlled file before execution began. A preflight validation pass was required to pass before any real inference call was made. This pass included the full automated test suite, a check that the deterministic ground-truth generator still reproduces the persisted ground-truth file, a live retrieval smoke query against the real vector index, a live smoke check of the structured sportsbook provider, and a direct check that the hybrid current-tool-data-precedence policy still behaves correctly. The experiment was then executed through one unified experiment runner rather than a separate script per architecture. This runner recorded every individual observation to an append-only raw results file, capturing architecture, scenario, repetition, and execution-order position, together with the full agent output, the evaluation result, and any failure.
After execution, we validated the dataset. The recorded run count matched the expected count of 330, with zero duplicate or missing keys across the architecture, scenario, and repetition dimensions. A full scenario-coverage matrix confirmed that every scenario had the expected number of observations under every architecture. Every raw result validated against its schema with zero errors. Ground-truth isolation and architecture-access-boundary audits both passed. Finally, a nine-way comparison of artifact fingerprints confirmed that every controlled input was unchanged from before the run to after it. Those fingerprints covered the benchmark data, both ground-truth files, the RAG corpus, the RAG index configuration, both system prompts, the canonical-query-template source, and the frozen configuration file itself.

3.7 Statistical Analysis
For proportion metrics, namely best-line accuracy, best-odds accuracy, freshness accuracy, and success rate, we report 95% Wilson score confidence intervals. We prefer these to the naive normal approximation, which behaves poorly near 0% or 100%, and this dataset includes several such cases. For paired binary outcomes, meaning whether a given observation's predicted best line, best odds, EV classification, or freshness judgment was correct, we used the exact binomial form of McNemar's test throughout. This form is appropriate given the modest discordant-pair counts involved. For paired continuous outcomes, namely EV absolute error, market-reference absolute error, completeness, and total latency, we used the Wilcoxon signed-rank test. For a three-architecture omnibus comparison on matched observations, covering completeness and latency at the individual-observation level and consistency at the scenario level, we used the Friedman test. We made three pairwise architecture comparisons for each metric, comparing RAG with TOOL, RAG with HYBRID, and TOOL with HYBRID, so we applied Holm-Bonferroni correction within each metric family independently and never pooled the correction across unrelated metric families. The alpha level of 0.05 and the correction method were fixed before any test was run and were not changed after observing results.

4. Results

(Reference: results/experiments/final_v1/analysis/analysis_table.csv, pairwise_comparisons.json, statistical_tests.json, and the figures under results/experiments/final_v1/analysis/figures/. See docs/RESULTS_ASSET_INDEX.md for the full asset list.)
Accuracy
RAG's observed best-line accuracy was 88.9% and its best-odds accuracy was 88.9%, both out of a valid paired N of 90 against each of TOOL and HYBRID. TOOL's and HYBRID's accuracy on both metrics was 100.0%, out of a valid paired N of 100 against each other. These values appear in Table 1 and Figure 1. The paired comparison between RAG and TOOL, and between RAG and HYBRID, on both best-line and best-odds accuracy provides evidence of a difference (exact McNemar, Holm-adjusted p=0.005859, raw p=0.001953, with an observed difference of -11.1 percentage points in both cases). The paired comparison between TOOL and HYBRID on both metrics was not statistically distinguishable at alpha=0.05 (Holm-adjusted p=1.0). The two architectures agreed on every one of the 100 paired observations, giving zero discordant pairs.
EV classification accuracy was N/A for all three architectures and for every pairwise comparison. Figure 2 shows this directly as labeled N/A bars rather than a fabricated zero. Every successful observation across all 330 landed in a quant insufficient data status. A valid best line was identified, but no observation gathered enough two-sided market data, meaning both outcomes of a market from enough sportsbooks, to compute a full EV verdict. This pattern held for RAG, TOOL, and HYBRID alike. We report it as an observed dataset characteristic, discussed in Section 5, and we did not correct, impute, or hide it.
Consistency
All three architectures showed mean, median, minimum, and maximum consistency of 1.000, with a standard deviation of 0.000, across the 11 scenarios with repeated observations (Figure 4). The Friedman omnibus test on the per-scenario matched consistency values was correctly degenerate. Every matched block was a three-way tie across architectures, so there was no rank variation to test (statistic=0.0, p=1.0). Consistency measures the reproducibility of an architecture's research-relevant output signature across repetitions rather than its correctness. A scenario on which an architecture fails identically on every repetition therefore also counts as consistent under this definition.
Freshness
All three architectures answered correctly on 10 of 10 observations of the single freshness-designated scenario in this benchmark (100.0%, with a 95% Wilson CI of [72.2%, 100.0%] in each case; Figure 3). No architecture made a freshness error, so every pairwise McNemar comparison had zero discordant pairs (Holm-adjusted p=1.0 in each case). The comparisons were therefore not statistically distinguishable by construction.
Secondary Metrics
RAG's median completeness was 0.75, compared to 1.00 for both TOOL and HYBRID. The RAG-TOOL and RAG-HYBRID comparisons, using the Wilcoxon signed-rank test, both show evidence of a difference (Holm-adjusted p=9.223e-11, raw p=4.611e-11, paired N=110). TOOL and HYBRID had identical medians and zero paired differences, so no test was performed between them. The unsupported-claim rate was 0.0% for all three architectures (Figure 5). This corresponds to zero unsupported claims out of 90 verifiable claims for RAG, 100 for TOOL, and 100 for HYBRID, and to zero observations with at least one unsupported claim for any architecture.
Median total latency was 16.159s for RAG, 6.952s for TOOL, and 22.696s for HYBRID (Figure 6; Table 1). All three pairwise Wilcoxon comparisons were statistically significant (RAG-TOOL Holm-adjusted p=3.844e-08, RAG-HYBRID Holm-adjusted p=7.021e-19, TOOL-HYBRID Holm-adjusted p=5.345e-19, all with paired N=110). The Friedman omnibus across all three was likewise significant (statistic=170.75, p=8.377e-38).
Failure Patterns
Of 330 total observations, 40, or 12.1%, were recorded as failures, and none were dropped from the dataset (Table 4). RAG had 20 failures under the category insufficient_retrieved_evidence, on scenarios S012 and S013, which are the spread and total market scenarios. TOOL had 10 failures under llm_output_invalid on scenario S012, and HYBRID had 10 failures under insufficient_current_data, also on scenario S012. All 20 of the TOOL and HYBRID failures on S012 are attributable to a client-side 180-second inference read-timeout on that scenario's tool-calling turns. This is an infrastructure characteristic of this local model and scenario pairing rather than a reasoning failure.
Hybrid Conflict Resolution
Across all 110 hybrid observations, the two information channels agreed 310 times and never disagreed, giving zero source conflicts (Table 5). Because no conflicts occurred, conflict-resolution accuracy is correctly reported as N/A rather than a fabricated value. Tool-only recoveries, meaning cases where sportsbook price data was available only from the tool channel, occurred 80 times. Zero stale RAG-only prices were incorrectly promoted to authoritative status, and zero source-reconciliation failures occurred.

5. Discussion

The clearest architecture effect in this dataset is that RAG's best-line and best-odds accuracy of 88.9%, along with its completeness median of 0.75, were both significantly lower than TOOL's and HYBRID's values of 100.0% and 1.00. TOOL and HYBRID were statistically indistinguishable from each other on both metrics. A plausible mechanism is that the canonical query used across all three architectures was deliberately kept architecture-neutral, since it names no sportsbooks and includes no per-architecture tuning. Semantic retrieval at a fixed top_k does not guarantee that both sides of a two-sided market, across enough sportsbooks, will be retrieved, whereas the tool-calling loop can request exactly the structured records it needs by name. RAG's 20 insufficient_retrieved_evidence failures on the spread and total scenarios (S012, S013) are consistent with this mechanism, though they do not prove it. Those two scenarios are market types with different underlying document coverage in the controlled corpus than the moneyline-heavy majority of scenarios.
A second finding holds across architectures. Zero of the 330 observations reached a full expected-value verdict. Because this pattern is present for RAG, TOOL, and HYBRID alike, it more plausibly reflects a model-capability characteristic of llama3.1:8b on this specific multi-step task than an architecture-design effect. The task requires gathering both sides of a market before a value comparison can be computed, and the same tool schema, system prompts, and quantitative engine are used regardless of which local model is configured. We did not modify the model, prompts, or tool schemas after observing this pattern. We report it as an honest dataset characteristic and as a candidate hypothesis for future work with a different model.
The structural guarantee in TOOL-calling and HYBRID, under which a final answer can only contain values actually returned by a validated tool call and never free-form model text, is consistent with the zero unsupported claims observed for all three architectures. RAG achieves the same outcome through its provenance validation, which serves an analogous role for retrieved evidence.
The hybrid architecture's deterministic conflict-resolution mechanism, under which current tool data always overrides a disagreeing RAG-derived price, is correctly implemented and independently verified. This dataset never exercised it in a live disagreement. The RAG-side extraction did not retain a validated price that disagreed with the tool-derived current price in any of the 110 hybrid observations. Observing the mechanism in action would require a scenario design in which the local model reliably extracts a disagreeing, provenance-valid stale price from the RAG corpus. This study's canonical, architecture-neutral query and this specific local model did not reliably produce such a case.
HYBRID's latency, with a median of 22.696s, reflects the combined cost of running both the RAG and tool-calling pipelines. It was the slowest architecture and offered no measured accuracy advantage over TOOL alone in this dataset. Whether that additional latency is worthwhile in a real deployment depends on whether the deployment specifically needs RAG's contextual and historical coverage in addition to TOOL's current-data reliability. This controlled, synthetic-benchmark study is not positioned to answer that question on its own.
These are observations from one controlled study, using one local LLM, one embedding model, and 11 scenarios with 10 repetitions each. We do not claim that these findings generalize to other models, other benchmarks, or production betting systems. The limitations are set out below.

6. Limitations

The benchmark is controlled and synthetic rather than live market data.
The scenario count of 11 and the repetition count of 10 per architecture and scenario are both finite, so statistical power is limited, especially for subgroup analyses.
Results are specific to the frozen local Ollama model, llama3.1:8b, and may not generalize to other local or frontier-hosted models.
Results are specific to the selected embedding model, sentence-transformers/all-MiniLM-L6-v2.
No live sportsbook API validation was performed.
The market-implied reference probability, computed as a no-vig leave-one-out consensus, is not the true win probability of the sporting outcome.
No independent predictive sports ML model was used or compared against.
Local LLM behavior may differ substantially from frontier hosted models.
This experiment does not establish real-world betting profitability.
The dataset shows local-model capability limitations directly. The model frequently did not gather two-sided market data, since 0 of 330 observations reached a full EV verdict, and the tool-calling turns for TOOL and HYBRID sometimes exceeded the inference client's 180-second timeout on scenario S012, producing 10 TOOL and 10 HYBRID failures that are all timeout-attributable rather than reasoning failures.

7. Future Work

Live sportsbook providers. A live-data OddsProvider could be implemented behind the project's existing provider abstraction, requiring no change to the tools, agents, or quantitative engine layered above it.
Broader scenario coverage. The 11-scenario representative subset used here could be extended to a larger and more varied set of controlled scenarios.
Alternative LLMs. This experiment could be repeated with other local models and with frontier-hosted models, using the project's existing configuration-driven provider selection. This would test whether the present findings, in particular the pervasive lack of a full EV verdict and the S012 timeout failures, are specific to llama3.1:8b.
Independent predictive ML model. Future work could introduce an independently trained and calibrated predictive model and compare its win-probability estimates against the existing market-implied no-vig consensus. This would test value signals that are independent of the market-derived reference probability, without changing the core architecture-comparison question studied here. This extension was not implemented as part of this project.

8. Conclusion

This controlled study finds no single agent architecture that dominates across accuracy, consistency, and freshness. Tool-calling and hybrid architectures achieved significantly higher best-line and best-odds accuracy, and higher completeness, than RAG-only, but they were statistically indistinguishable from each other on every binary accuracy metric measured. The hybrid architecture was significantly slower than tool-calling alone and offered no measured accuracy benefit in this dataset. Consistency and freshness showed no statistically distinguishable difference between any pair of architectures, because no architecture in this study produced inconsistent or stale-affected output on the scenarios evaluated. To answer the research question directly, architecture affects accuracy and completeness, favoring tool-calling and hybrid over RAG-only, and it affects latency, favoring tool-calling over hybrid. It did not produce a measurable difference in consistency or freshness in this controlled experiment. The answer is therefore architecture-dependent and metric-dependent rather than a single ranking.
