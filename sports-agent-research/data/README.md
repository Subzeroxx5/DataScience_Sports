# Data

This directory holds controlled, **synthetic** data used for experiments. No
record in this directory represents a live or historical real-world
sportsbook price. All odds, teams, games, and probabilities are fabricated
for the purpose of this research prototype and must never be presented as
real betting information.

## Files

| File | Purpose |
|---|---|
| `current_odds.json` | Flat ledger of current, structured sportsbook prices. Read by dataset loaders (`src/evaluation/dataset.py`) and, later, by Milestone 5 sportsbook tools. |
| `historical_odds.json` | Flat ledger of stale/superseded prices for the 3 freshness scenarios. Not used to build `TestScenario` objects — reserved for Milestone 6 RAG document ingestion, so RAG can be given outdated odds while tools see current ones. |
| `test_scenarios.json` | Scenario definitions: game, market, and the experiment's reference probability. References `current_odds.json` by `game_id` rather than duplicating odds data. |
| `ground_truth.json` | Deterministically generated by `python -m src.evaluation.ground_truth` from `test_scenarios.json` + `current_odds.json` via `src/calculations/odds_math.py`. Never hand-edited. |
| `rag_documents/corpus.jsonl` | Deterministically generated by `python -m src.rag.build_corpus` from `current_odds.json` + `historical_odds.json` + `test_scenarios.json`'s `game`/`market.market_type` fields only (never `estimated_true_probability`, `category`, or `ground_truth.json`). One validated `RagDocument` (`src/rag/documents.py`) per line. Never hand-edited. |

## Sportsbooks

A fixed, controlled set of four sportsbook names is used throughout:

```text
DraftKings
FanDuel
BetMGM
Caesars
```

These are used only as controlled data-source labels for this research
prototype, not as an endorsement or representation of real sportsbook
pricing.

## Scenario Structure

Each entry in `test_scenarios.json` has:

```text
scenario_id                    unique identifier, e.g. "S001"
category                       descriptive tags for humans only — dataset
                                and ground-truth tests verify coverage from
                                the actual computed data, not these tags
game                            game_id, home_team, away_team, start_time, sport
market                          market_type (moneyline/spread/total), selected_outcome, line
estimated_true_probability      see below
current_odds_version             version tag copied into ground truth for
                                traceability (e.g. "v1")
```

The odds themselves are **not** embedded in `test_scenarios.json`; they are
looked up from `current_odds.json` by the full `(game_id, market_type,
selected_outcome)` combination when a `TestScenario` Pydantic object is
built (`src/evaluation/dataset.py::build_test_scenario`) — the same key
`ControlledOddsProvider` (`src/providers/controlled.py`) uses to index
odds. Filtering by `game_id` alone would be ambiguous now that a single
game can hold odds for both sides of a market (see "Two-Sided Markets"
below).

## Estimated True Probability

`estimated_true_probability` is **not** a claim about the real-world
probability of any outcome. It is the experiment's assumed reference
probability, used only to calculate deterministic ground truth (implied
probability, expected value, positive/negative EV classification) via
`src/calculations/odds_math.py`. Treat it as a controlled experimental
input, not a forecast.

## Current vs. Stale Records

`current_odds.json` records always have `"is_current": true`.
`historical_odds.json` records always have `"is_current": false` and an
earlier `"timestamp"` than their current counterpart, plus `"version":
"v0"` (vs. `"v1"` for current). Three scenarios (`S009`, `S010`, `S011`)
each have exactly one sportsbook with a stale counterpart record, so later
architecture comparisons can test whether an agent uses the current price
or an intentionally outdated one.

## Missing-Data Policy

A sportsbook that does not offer a line for a scenario is **omitted
entirely** from `current_odds.json` for that `game_id` — it never appears
with `american_odds: 0`. `american_odds = 0` remains invalid at the
`SportsbookOdds` model level (Milestone 2) and is never used to represent
"no data." Ground truth's `expected_sportsbooks` field reflects only the
sportsbooks actually present, so completeness can be measured against it
(`S008` is the missing-data example: FanDuel is absent).

## Tie Policy

When multiple sportsbooks offer equally favorable odds for the best price
(same implied probability, e.g. two books both at `+125`), ground truth
preserves **all** of them in `expected_best_sportsbooks` (sorted
alphabetically), not just one. `expected_best_sportsbook` (singular, kept
for Milestone 2 backward compatibility) is set to the first name in that
list. Evaluation code should treat any sportsbook in
`expected_best_sportsbooks` as a correct best-line answer. `S007` is the
tie example (`DraftKings` and `FanDuel` both at `+125`).

## Two-Sided Markets

For 4 games (`G-2026-001`, `G-2026-007`, `G-2026-008`, `G-2026-009`),
`current_odds.json` holds current moneyline odds for **both** teams, not
just the scenario's `selected_outcome`. This exists so a future no-vig /
market-consensus calculation (Milestone 7) can pair a sportsbook's price
on each side of the same market.

No new schema field (e.g. `market_id`) was introduced. Market identity is
the tuple `(game_id, market_type)`: this dataset never has more than one
active market per `(game_id, market_type)` pair, so the two mutually
exclusive moneyline outcomes are always exactly `Game.home_team` and
`Game.away_team`. A sportsbook's two prices for the same market are paired
deterministically by querying the same `(game_id, sportsbook,
market_type)` with each of the two outcome strings — e.g.
`get_sportsbook_odds("G-2026-001", "DraftKings", MONEYLINE, "Los Angeles
Lakers")` and the same call with `"Boston Celtics"`.

Adding a second outcome's odds under the same `game_id` surfaced a latent
bug in `build_test_scenario`'s old game_id-only filter (it would have
pulled both sides' records into one `TestScenario`, tripping the
no-duplicate-sportsbook validator). The filter was corrected to match
`ControlledOddsProvider`'s existing `(game_id, market_type,
selected_outcome)` indexing; `ground_truth.json` is unaffected — byte-
identical before and after — because each existing scenario's own
outcome's records are unchanged.

Existing scenario IDs, game IDs, tie behavior (`S007`), missing-sportsbook
behavior (`S008`, FanDuel absent on both sides), and the freshness
stale/current pair (`S009`, `DraftKings` on the Timberwolves side only)
are all unaffected. No new `TestScenario` entries were added for the
opposing outcomes — they exist only as raw `current_odds.json` records,
retrievable through the provider/tool layer but outside the 14-scenario
ground-truth benchmark.

## RAG Corpus

`rag_documents/corpus.jsonl` is what the future RAG-only and hybrid
architectures retrieve from (no embeddings/vector store/retriever exist
yet — Milestone 6C). Regenerate it with:

```bash
python -m src.rag.build_corpus
```

Three document types (`RagSourceType` in `src/rag/documents.py`):

- `sportsbook_snapshot` — one sportsbook's price for one outcome, as text.
  Generated from every moneyline record in `current_odds.json` (current)
  and every record in `historical_odds.json` (stale, `is_current=false`,
  older `timestamp`/`version="v0"`, values unaltered from the source
  file). Spread/total records are excluded, matching this project's
  "moneyline is the core EV-analysis market" convention (see "Market Type
  Scope" below).
- `game_context` — one generic, template-based note per game. No odds, no
  market information, no hint about any sportsbook or price.
- `market_context` — one generic note per moneyline market, stating only
  that multiple sportsbooks track it. Content is identical in structure
  for every market regardless of the actual odds, so it cannot leak
  anything about relative pricing.

**Ground-truth leakage is a hard requirement.** No document — and no
field on `RagDocument` — may express `expected_best_sportsbook`,
`expected_best_odds`, `expected_ev`, `expected_positive_ev`,
`estimated_true_probability`, a consensus/no-vig probability, or
equivalent natural-language claims ("X is the best sportsbook", "this
line has positive EV"). `src/rag/build_corpus.py` never imports
`src.evaluation.ground_truth` and never reads `estimated_true_probability`
or `category` from `test_scenarios.json` — only `game` and
`market.market_type`/`selected_outcome`. `tests/test_rag_corpus.py` scans
every generated document's full serialized JSON for a list of forbidden
field names and phrases as a second line of defense.

Two-sided markets (`G-2026-001`, `G-2026-007`, `G-2026-008`, `G-2026-009`
— see "Two-Sided Markets" above) each have `sportsbook_snapshot` documents
for **both** outcomes, sharing the same `market_id` (`"{game_id}-moneyline"`)
so a future retriever/agent can reconstruct the full market.

Corpus generation reads the benchmark files as pure input and never
modifies them; `tests/test_rag_corpus.py` verifies their hashes are
unchanged after generation. Generation is fully deterministic (no
`uuid4()`, `datetime.now()`, or `random`) — document IDs and content are
fixed functions of the source data, verified byte-for-byte identical
across repeated runs.

## Ground Truth Generation

Ground truth is produced only by deterministic Python calculations — never
by an LLM, RAG, or a hard-coded expected value. Regenerate it with:

```bash
python -m src.evaluation.ground_truth
```

This reads `test_scenarios.json` + `current_odds.json`, computes best odds,
implied probability, expected value, and positive/negative EV classification
via `src/calculations/odds_math.py`, and writes a sorted, deterministic
`ground_truth.json`. Running it twice against unchanged source data produces
a byte-identical file.

## Market Type Scope

`S012` (spread) and `S013` (total) exist to exercise the `Market` schema
across all supported market types, and ground truth is still computed for
them using the same generic American-odds math. However, they are marked
`schema_validation_only` in `category`: the initial experiment's EV
comparison across architectures is expected to focus on moneyline
scenarios, where the probability interpretation is least ambiguous.
